まずは分野を均等にした。実務の発生頻度を代表する標本ではない。各分野は10分類・各10件で、複雑さの設計上の配分は基礎40・複数条件40・応用20。これはモデルの成績予想ではない。

## 実行と評価

ユーザーから、一覧作成後にGemma4 26Bで実行・評価し、CUDA時は承認待ちせず再起動・再試行してよい旨の指示を受けている。実行前に各対象の入力、編集範囲、合格条件を具体化しhashで固定する。

コードは既存bounded経路への適合性を確認する。Officeはファイル生成・既存ファイル編集・GUI操作を区別し、実行可能と事前認定しない。Office用の補助実装を使う場合は、その役割を明示する。現在のProduction Routerや既存の実験条件を暗黙に変更しない。

複数アプリ業務100件は、単一LLM呼出しのタスクではなく、分割と統合を含む親タスク。子タスクを後で増やしても、元の500件の分母へ重複加算しない。

### 成績の扱い

- 初回の実出力を保存する。失敗しても条件や正解を変えない。
- モデル不正解、形式違反、OUTPUT_LIMIT、context不適合、環境障害、未実行を別々に記録する。
- CUDA時は失敗runを残し、新しいrun IDで最大1回のインフラ再試行を行う。無制限に障害を再現させない。
- 自動検証だけでは判定できない見た目や文章の品質は、未確認をPASSにしない。
- 実アプリ動作・数式再計算・印刷・リンク等は、確認した範囲と未確認を分ける。
- Gemma単体でできたかと、Host・Codexの補助で完成したかを分ける。Codexが修正した成果物をGemma単独PASSにしない。
- Codex tokensとCreditsは取得できた実usageだけを記録する。欠測はnullとし、Local tokensを節約量に換算しない。

## 一覧の限界

タイトルの完全重複はない。過去の全実験や公式課題との意味上の重複照合は未完了であり、未使用を検証済みとは主張しない。実行対象を固定する前に重複・近似・意図した対照関係を記録する。

分野間には、同じ操作を別形式で使う課題や、既存の処理を不具合修正として扱う課題もある。500件を独立な500種類の能力、または一般的な業務成功率の無作為標本と解釈しない。テンプレート学習と評価では、類似課題を同じグループとして分ける。

## 知識として残すもの

適用条件、分割方法、渡した参照、合格判定、失敗理由、準備・検証・レビューを含む費用を残す。成功した分割を使い回せるテンプレートへ整理する。既存の実測や旧STOPは変更しない。
