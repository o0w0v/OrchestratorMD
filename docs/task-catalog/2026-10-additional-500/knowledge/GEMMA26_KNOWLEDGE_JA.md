# Gemma4 26Bへ任せやすい作業

追加500件から、8つの作業を条件・検査とセットで登録した。数値は実行前に固定した狭いチェックの初回通過数であり、実業務全体の成功率ではない。

| 作業 | 実測 | 渡すときの条件 |
|---|---:|---|
| 問い合わせの分類・分岐を行う小関数 | 10/10 | 型、優先順位、戻り値、変更する関数bodyを固定 |
| 申請・承認状態を扱う小関数 | 10/10 | 状態の意味と判定条件を列挙 |
| 範囲の小さい既知不具合修正 | 10/10 | 不具合箇所と回帰テストが既知。自由な原因調査とは区別 |
| Excelの入力整理 | 9/10 | 列型、入力例、編集欄を固定 |
| Excelの限定された基本計算・数式 | 9/10 | 条件の優先順、丸め、参照範囲を指定しnative再計算 |
| PowerPointの局所編集 | 9/10 | 編集する要素・属性をHostが指定 |
| PowerPointの指定書式の統一 | 10/10 | 色や書式が指定済み。自由なデザイン評価とは区別 |
| Wordのスタイル・ページ設定 | 9/10 | 利用できるstyle名と編集欄を提示 |

Rustは関数body生成とcompile/test、OfficeはGemmaのtyped JSONをHostが実ファイルへ変換する方式だった。OfficeのGUI操作、資料全体の完成品質、画像理解の能力を示す数値ではない。小関数でもfmt/clippyや実アプリ統合、独立した最終レビューは別途必要である。

## 苦手側も原因を分けて登録する

**実出力で誤りを確認したもの**：COD-025/060の境界・区間集約、WRK-036/045/066の計算や表と説明の矛盾、XLS-016/052の条件順序・集合差分。補完モデルの診断では、まずこのような具体例を使う。

**まだ能力の低さと断定しないもの**：要約や手順書の低いraw通過数には、妥当な別表現を落とす完全一致採点も含まれる。改善すべき採点条件を先に確認する。

**モデル交換の対象から除くもの**：PPT-020の軸がnativeファイルへ反映されないHost不備、XLS-087の配列要素型の説明不足とHost例外、DOC-025の複数ページ検証不足。別モデルが合格しても、これらのHost・契約上の問題が解消した証拠にはならない。

## 知識1項目に残す情報

「作業」「入力と型」「変更範囲」「必要な参照」「合格判定」「成功/失敗Task ID」「model digestと設定」「補助実装の役割」「未測定範囲」を保存する。各項目の成功数はその条件での結果として扱い、一般的な成功確率へ変換しない。

登録内容は[GEMMA26_KNOWLEDGE.json](GEMMA26_KNOWLEDGE.json)に保存した。Production Routerへの自動採用やcross-model fallbackは有効化していない。
