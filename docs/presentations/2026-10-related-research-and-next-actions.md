# Codex＋ローカルLLM委譲の関連研究と、次に活かせること

調査日：2026年10月22日  
[発表資料「余ったGPUでCodexは安くなるのか？」](2026-10-codex-local-llm-delegation.md) の補足。

## まず押さえたいこと

今回の構成に近い研究は、主に次の3つに分かれる。

1. **振り分ける**：どの仕事を小さいモデルへ任せ、どの仕事を強いモデルへ回すか。
2. **分割する**：実行役が扱える大きさまで、仕事をどう分けるか。
3. **使い回す**：成功した分割や作業手順を、次の仕事でも利用する。

これまで約50件規模で得た成功・失敗・費用の実測は、結果として受け入れる。その結果を起点に、**さらに約500件を追加**し、仕事の種類や難しさによる違いを調べる。既存分を含めて合計500件にする、という意味ではない。

以下の「今回への活かし方」は、本プロジェクト側の提案である。論文がCodex＋Gemma26の構成や同じCredits削減率を実証した、という意味ではない。

## 1. 今の仕組みに近い研究

| 研究 | 論文が扱う仕組み | 今回への活かし方 | 違い・注意点 |
|---|---|---|---|
| [FrugalGPT: How to Use Large Language Models While Reducing Cost and Improving Performance（2023）](https://arxiv.org/abs/2305.05176) | 複数モデルを組み合わせ、必要に応じて強いモデルを呼び出し、品質と費用を両立する。 | Gemmaを先に試し、採用できなければCodexへ回す流れを、失敗費用も含めて考える。 | 論文の費用削減率を、今回のモデル・課題・Creditsへそのまま当てはめない。 |
| [RouteLLM: Learning to Route LLMs with Preference Data（2024）](https://arxiv.org/abs/2406.18665) | 回答の好みを示すデータなどから、強いモデルと弱いモデルの振り分け方を学ぶ。 | 追加評価の実績を蓄積し、将来の「Gemmaへ任せる条件」を作る参考にする。 | 公開routerが今回のモデル対やOffice業務で、そのまま有効だと考えない。 |
| [ADaPT: As-Needed Decomposition and Planning with Language Models（2024）](https://aclanthology.org/2024.findings-naacl.264/) | 実行役がタスクを実行できない場合に、計画役が必要な分割を行う。実行役の能力に応じて分割の深さを変える。 | 「どこまで細かくすればGemmaが扱えるか」と「分割自体の費用」を調べる参考にする。 | 論文は失敗後の再分割も使う。現在のone-shot／repair 0へ、自動で再試行を追加する根拠にはしない。 |
| [Agent Workflow Memory（2024）](https://arxiv.org/abs/2409.07429) | 過去の実行経験から再利用できる作業手順を取り出し、後のタスクで利用する。 | 成功したタスク分割をテンプレートとして蓄積する。毎回ゼロから計画しない仕組みの参考になる。 | 主な評価対象はWeb操作。コーディングやOfficeでも同じ効果が出るかは別途測る。 |

### 分割の設計をもう少し読むなら

[Decomposed Prompting: A Modular Approach for Solving Complex Tasks（2022公開／ICLR 2023）](https://arxiv.org/abs/2210.02406) も参考になる。複雑な課題を小さな処理へ分け、それぞれを専用の処理役へ渡す研究。

今回なら、型情報の抽出や形式チェックなど、決定的に処理できる部分をHostへ任せ、LLMには生成が必要な部分を担当させる、という設計を考える材料になる。ただし論文の評価は主に記号的な推論や質問応答であり、今回の実装品質を保証するものではない。

## 2. PPT・Excel・事務作業へ広げるための研究

| 研究 | 何を評価するか | 追加評価への参考 |

これらは追加課題の分類や採点方法の参考資料。データセットのそのままの採用、追加download、ベンチマーク実行を決定するものではない。Wordを含む各業務の具体的な課題数・配分は、別途決める。

## 3. 今の次のアクションへどうつなげるか

### ① 既存結果を残し、追加約500件で範囲を広げる

既存の結果と追加評価は、別のまとまりとして保存する。コードだけでなく、PPT・Excel・Wordなどの業務も候補にする。

各課題では、少なくとも次を揃える。

- 何を完成させる仕事か。
- 作業場所が最初から分かるか、探索が必要か。
- 必要な手順数、参照する型・資料、ほかの処理とのつながり。
- 最初の出力をそのまま採用できたか。
- 不採用なら、内容・形式・範囲・環境のどこに問題があったか。
- 最終品質、Codexの実usage・換算Credits、Local usage、待ち時間。
- タスク設計・参照情報・テストを準備する費用や手間。

「難しい」という一語だけでまとめず、何が難しさを増やしたかを記録する。Office課題では、コード生成と完成ファイルの編集・画面操作を区別する。500件集めれば、あらゆる業務へ一般化できるという保証はない。

### ② 成功した分割を、同時にテンプレート化する

Agent Workflow MemoryとDecomposed Promptingを参考に、次のような形で知識を残す。

| 項目 | 残す内容 |
|---|---|
| 適用条件 | どんな依頼・入力に使える手順か |
| 分割手順 | 各部分を何の責任で切り分けるか |
| 必要な参照情報 | 型、helper signature、公開資料、入力ファイルなど |
| 完了条件 | 各部分と、組み合わせ後の全体をどう確認するか |
| 失敗条件 | 任せない方がよかった条件や、過去の失敗理由 |
| 実績と費用 | 使用した課題ID、成功・失敗、計画・検証を含む費用 |

これは今回提案する記録形式であり、論文のschemaをそのまま転載したものではない。

テンプレート作成に使った課題と、その有効性を確認する課題は分ける。同じ課題の言い換えだけで成功率が高く見えないようにする。

### ③ データとテンプレートが整ってから、全体の経済性を再比較する

振り分けにはRouteLLM、モデル切替の費用設計にはFrugalGPTを参考にする。ただし、今すぐ既存Routerを置き換えない。

次のA/B比較では、実装費用だけでなく、計画・分割・参照情報・検証・レビュー・失敗後のCodex実装まで含める。取得できないusageはnullのままとし、Local tokensをCodex tokens savedへ読み替えない。

最終的には、**品質を保ったまま、タスクの準備も含めたCodexの仕事とCreditsが減るか**を確認する。

## 4. 読む順番

1. **ADaPT**：実行役に合わせ、どこで分けるか。
2. **Agent Workflow Memory**：分け方や手順をどう使い回すか。
3. **OfficeBench／SpreadsheetBench／PPTAgent**：業務課題と採点基準をどう作るか。
4. **RouteLLM／FrugalGPT**：蓄積後に振り分けと費用をどう最適化するか。
5. **Decomposed Prompting**：分割と処理役の組合せを設計する補助資料。

## 5. この調査で変更・実行していないこと

この文書は、関連研究と次の検討事項をまとめたもの。既存の実測値・旧STOP・公式課題・採点・Router・bounded 2.2.8を変更していない。追加500件の課題配分や実行条件も凍結していない。

研究の実験結果と本プロジェクトの実測は別々に扱う。論文の削減率を、Codex＋Gemma26の達成値として引用しない。
