# 余ったGPUでCodexは安くなるのか？
## ローカルLLMへのタスク委譲で試したこと、分かったこと、残った課題

> **発表用ストーリー・構成案（2026年10月22日）**  
> 主題：品質を維持しながら、Codexのクレジット消費を減らせるか。  
> **一番伝えたいこと：安いモデルに仕事を丸投げしても安くならない。どの仕事を、どんな条件で任せるかが重要だった。**

この文書は発表の台本・スライド化の土台。検証ログそのものではない。数値は末尾の公開済み実測報告に基づく。初期試行の説明は取り組みの経緯をまとめた定性的な整理であり、すべての試行で同一の損益になったという意味ではない。

---

## 1. 背景・動機 — PCは暇なのに、Codexの使用量は減る

### 今回登場する2つのAI
- **Codex**：クラウド上のAIを使って、プログラムの設計・作成・修正などを手伝ってくれるツール。便利だが、使える量にはプランごとの制限がある。
- **Gemma26**：自宅PCのGPUを使って動かすAI。今回はこちらに、Codexの仕事の一部を任せてみた。

今回はCodex側のAIとして **GPT-6 Sol** と **GPT-6 Astra** の2種類を比較した。両者は使用量あたりのCreditsの計算条件が異なる。

### Codexの課題
- Codexは設計、コード実装、デバッグまで便利だが、使い続けるとクレジット消費やプランごとの使用量制限が気になる。
- 特に、単純な実装や繰り返しの修正にも高性能モデルを使うのは、必ずしも効率的ではないのではないか。

### 一方で、自宅PCに余剰リソースがあった
自宅PCを使う時間が以前より減り、使っていない計算能力を活用したかった。

| 主な構成 | スペック |
|---|---|
| CPU | Intel Core i7-13700K |
| GPU | NVIDIA GeForce RTX 3080 10GB |
| RAM | 64GB |
| ローカルLLM | Ollama + Gemma4:26b（Q4_K_M） |

※ 検証時のドライバー・Ollama・モデルdigestや量子化条件は各実験のfreezeを参照。GPU 10GBというVRAM制約もある。

**ここでの発想：Codexがすべて生成するのではなく、自宅PCにあるローカルLLMを実装担当として活用すれば、クレジットを節約できるのでは？**

## 2. 目的 — 「ローカル化率」ではなく「品質を維持した節約」

目的は、Gemmaに任せるタスク数を最大化することではない。

1. Codex単独と同等の最終品質をできる限り維持する。
2. Codexの入力・キャッシュ入力・出力トークンと、凍結したStandard単価から換算したCreditsを削減する。
3. 失敗した仕事は安全にCodexへ戻す。Local候補や診断の漏えい、誤採用を防ぐ。
4. どんなタスクなら節約になり、どんなタスクでは逆に高くなるかを知る。

**注意：Creditsはnative CLIの実測usageに凍結単価を適用した換算値。アカウント残高から確認した実引落額ではない。** また、ローカルの電力・設備費、検証準備・監督の全工数を含むプロジェクト純利益は未算出。

## 3. やったこと — 失敗から設計を変えた

### 試行①：CodexからGemmaへ、依頼をほぼそのまま渡す
- 発想はシンプル。「Codexがやる実装を、代わりにGemmaへ依頼する」。
- しかし、元依頼にはリポジトリの文脈、変更対象、依存関係、受入条件などが含まれ、Gemmaにとって大きすぎる・曖昧な仕事になる場合があった。
- Gemmaが失敗すると、Codexによる原因確認や再実装が必要になる。**Gemmaを呼んだだけでは節約にならず、追加のCodex使用量で割高になる場合があった。**

**学び①：委譲そのものは節約ではない。失敗処理まで含めて比較する必要がある。**

### 試行②：Gemmaに修正をもう一度依頼する
- エラーを返してGemmaに再試行させる方法も試した。
- 再試行するほど、検証、レビュー、状況整理などの費用も増える。
- 初期の検証では、やり直しを重ねるより、Codexが直接解いた方が安いケースが見られた。
- **「2回目を行うと必ず高い」ではなく、「失敗しやすいタスクでは再試行の追加費用が節約分を超える場合がある」**という教訓。

**学び②：再試行回数を増やす前に、最初に渡すタスクを変えるべき。**

### 試行③：Gemmaに任せる仕事を、小さく・分かりやすくする
Gemma26へ渡す必要情報・修正場所・受入条件を事前に固定し、小さな作業を依頼する方式を試した。

**実測経路の訂正（2026-10-29）：内部46課題では、固定した作業指示をGemmaへ直接渡した。別途実行した共有Codex Plannerの計画出力はGemmaへ入力していないが、その費用は比較に含む。「最初のCodexがGemmaへの指示を毎回作る効果」を測った試験ではない。仕様・編集範囲・テストを準備する全費用も未測定。**

#### まずは簡単な図

~~~mermaid
flowchart TD
    A["事前に固定した仕様・編集範囲・テスト"] --> B{"固定ルールでGemmaの対象か"}
    B -->|"はい"| C["Gemma26が1回だけ作る"]
    B -->|"いいえ"| D["Codexが作る"]
    C --> E{"テストとレビューに合格？"}
    E -->|"はい"| F["採用"]
    E -->|"いいえ"| D
    D --> G{"テストとレビューに合格？"}
    G -->|"はい"| F
    G -->|"いいえ"| H["不採用として記録"]
~~~

**ポイント：Gemma26が一度で完成できれば節約につながる。失敗時はCodexに戻すが、その分の手間と使用量も増える。**

#### 詳しい仕組み（参考）
以下は同じ流れを、技術的な役割ごとに表した図。

- **固定Task契約**：仕様、変更対象、型・インターフェース、参照情報、受入条件、禁止範囲を実行前に固定する。
- **共有Codex Planner**：内部46件では別途実行し比較費用へ計上。ただし、その計画出力をGemmaへ渡していない。検査の準備を実行中に自動作成したという意味ではない。
- **Router**：単一責務で編集領域が明確な実装のみGemmaに回す。高リスク・複雑・曖昧なタスクはCodexへ。
- **Gemma26 Worker**：固定領域を原則一回だけ生成する（今回のbounded 2.2.8評価はone-shot / repair 0）。
- **Host Validation**：スコープ、構文、テスト、Lint、変更禁止領域などを確認する。
- **独立Codex Reviewer**：Host PASSだけで採用せず、要求仕様・実装の妥当性をレビューする。
- **Clean Fallback**：不採用時は、Gemmaの候補・失敗診断を渡さずにCodexが初期状態から実装する。

~~~mermaid
flowchart TD
    U["事前固定のTask契約：仕様・範囲・テスト"] --> R{"固定Router：Gemmaの対象か"}
    P["共有Codex Planner：別途実行・会計計上。Gemmaへの入力なし"]
    R -->|"Yes"| L["Gemma26：範囲限定・1回生成"]
    R -->|"No"| C["Codex Executor：直接実装"]
    L --> H["Host：テスト・Lint・スコープ検証"]
    H -->|"PASS"| V["独立Codex Reviewer"]
    H -->|"FAIL"| C
    V -->|"ACCEPT"| O["候補を採用"]
    V -->|"REJECT"| C
    C --> D["Host検証＋独立レビュー"]
    D --> G{"Codex側も合格？"}
    G -->|"はい"| O
    G -->|"いいえ"| N["不採用・結果を記録"]
~~~

※ 実際の検証では、Gemma26には事前に固定した小さな作業指示を入力した。Codexの計画書全文をそのまま渡したわけではない。

**学び③：作業の境界と検査を先に固定した小さな仕事で、実装をLocalへ置き換える効果が出た。自動のタスク分解・検査生成の効果だけを分離した結果ではない。**

## 4. 実測結果 — 小さな仕事では効果あり

### 小さなプログラム作成・修正を、同じ44課題で比較

ここで比べたのは、**作るものや直す場所があらかじめ決まっている、小さなプログラム作成・修正の仕事**です。大きなシステム全体を作るような仕事ではありません。

**前提：仕様・編集範囲・テストを先に用意した課題の比較。自由な依頼から検査を準備する全費用を含む削減率ではありません。**

発表では、**Codexだけで行った場合と、Gemma26を併用した場合の両方で、最後まで品質を確認できた44課題**を比較します。

**GPT-6 Solでの比較（同じ44課題）**

| 構成 | テスト・レビュー合格 | 換算Credits |
|---|---:|---:|
| Sol-only | 40/44件 | 145.37 |
| **Sol＋Gemma26** | **44/44件** | **85.71** |

→ **Credits 約41%削減**。Codexの使用トークン数も約47%減りました。

**GPT-6 Astraでの比較（同じ44課題）**

| 構成 | テスト・レビュー合格 | 換算Credits |
|---|---:|---:|
| Astra-only | 44/44件 | 671.25 |
| **Astra＋Gemma26** | **44/44件** | **445.19** |

→ **Credits 約34%削減**。Codexの使用トークン数も約42%減りました。

※ Solの44課題とAstraの44課題は、比べるモデルごとに選んだ対象が一部異なります。**同じモデル内の2方式を比べるときは、同じ44課題同士**にしています。比較対象の決め方・小数点以下の正確な数値は下記の補足に記載します。

- 元の実験では各方式について**46課題を対象として試行**した。Gemma併用経路ではそれぞれ2課題がCUDA／Host Formatterなどの障害で品質判定まで到達しなかった。よって、**「最初から44課題だけを実験した」とは説明しない**。
- 発表用には、各モデル内の両方式で最後まで評価できた**対応する44課題を事後的に抽出**した（SolとAstraで抽出対象は一部異なる）。

**小さな仕事に限って比較すると、Gemma26に任せることでCodexの使用量を大きく減らせました。**

## 5. なぜ公式課題で効果が縮小したのか？

### 理由①：そもそもGemmaに任せない仕事が多い
公式30件では、事前に **15件がGemma適格、15件がCodex直接**と判定された。特にMulti-SWE-benchの10件は全て直接経路。

採点済み29件のSol-only Creditsのうち、**282.85 / 358.35（約79%）はLocal不使用のDirect14件**で消費していた。削減できる領域が限られていた。

### 理由②：Gemmaが作ったコードを採用できる割合が下がった
| | 小さな仕事（評価済み44課題） | 公開ベンチマークのうちGemmaへ任せた15課題 |
|---|---:|---:|
| Solを使った場合 | 37/44（84.1%） | 6/15（40.0%） |
| Astraを使った場合 | 38/44（86.4%） | 4/15（26.7%） |

公開課題では、求められる動作やチェックが厳しくなることもあります。ただし、**単純に「Gemmaが難しい問題を解けないから」とは言い切れません**。コードの書き方がルールに合わない、チェックで止まる、Codexの最終確認で採用されない、といった理由もありました。

※ 左列は発表に使う評価済み44件だけの採用数を再集計した値。元の46課題全体での採用率（Sol 37/46、Astra 38/46）とは分母が異なります。

### 理由③：失敗時のFallbackが追加費用になる
- 公式Sol構成：Local採用6件、Clean fallback9件。
- 公式Astra構成：Local採用4件、Clean fallback11件。
- 公式SolのLocal適格15件だけなら Credits **75.49859 → 68.16259（9.72%減）**。
- 公式Astraの同15件では Credits **271.80135 → 280.45510（3.18%増）**。

Gemmaの試行と検証を行ったうえで高額なExecutorに戻ると、節約を相殺し得る。

### 理由④：作ったプログラムが、そのまま採用できるとは限らない

Gemma26が作成したプログラムは、そのまま使用せず、2段階のチェックを実施した。

1. **自動チェック**：プログラムが正しい形式で書かれ、テストを通過するか確認する。
2. **Codexによるレビュー**：要求された内容を正しく実装できているか確認する。

Astra＋Gemma26の検証では、15件のうち7件が自動チェックで不合格となり、さらに4件がCodexのレビューで不採用となった。

結果として、**実際にGemma26のプログラムを採用できたのは15件中4件だった。**

また、開発中のチェックと公式採点では一部の実行環境が異なり、開発中に合格したプログラムが公式採点では不合格になる例もあった。

**今後は、Gemma26の実装精度だけでなく、依頼内容の伝え方やチェック方法も改善する必要がある。**

## 6. これから — もっと難しい仕事にも使えるようにしたい

今回分かったのは、**Gemma26は、小さく内容がはっきりした仕事なら効果を発揮しやすい**ということ。

一方、実際の開発では、複数の場所を同時に直したり、ほかの機能とのつながりを考えたりする必要がある。そうした仕事を、今の仕組みではまだうまくGemma26へ任せられない。

今後は、次のことに取り組みたい。

1. **大きな仕事を、小さな仕事に分ける**  
   Codexが全体を考え、Gemma26が担当できる部分を切り出す。最後に、各部分を組み合わせても正しく動くか確認する。
2. **最初に「任せるかどうか」を判断する**  
   Gemma26には得意な仕事だけを任せ、難しい仕事は最初からCodexが担当する。失敗して作り直す無駄を減らしたい。
3. **プログラムのチェック方法を改善する**  
   Gemma26のコードが採用されなかった原因を調べ、書き方のルールやチェック環境の違いによる問題を減らす。間違ったコードを採用しないことも大切にする。
4. **実際の開発に近い仕事でも試す**  
   小さな練習課題だけでなく、もう少し複雑な開発作業でも、正しく動くか・どのくらい節約できるか確かめる。
5. **本当にお得かを考える**  
   CodexのCreditsだけでなく、自宅PCの電気代や運用の手間も含めて、どのくらいメリットがあるか確認する。

**目指す姿：Codexに何でも任せるのでも、Gemma26に丸投げするのでもなく、それぞれの得意な仕事を分担して、品質を落とさず費用を減らす。**

### 最後の一言

> **ローカルLLMを入れるだけでは安くならなかった。**

## 8. 発表者向け補足（スライドには載せない）

- 内部46件は独自の小規模課題であり、公式30件とは難易度・費用分布が違う。削減率を直接同一条件のように並べない。
- 元の内部46件には各Routerで品質判定に至らない2件がある。発表の主表は**各モデル内で両経路が評価完了した同一44課題だけの事後的補助分析**であり、46件完走の結果として扱わない。Sol用とAstra用の44件は課題集合が異なる。公式30件にもTracing 1件の環境未測定があり、全30完了とは言わない。
- 「公式29件でSol Routerは同じ21件を解決し、Creditsを6.46%減らした」は観測事実だが、**6.46%すべてがGemmaの因果効果ではない**。直接経路にも費用差がある。
- 公式にはfalse greenが残るため、Production品質保証は未達。
- 初期試行の定性的説明に具体的な削減率・再試行損益を付ける場合は、対象runの根拠を追加してからにする。
- Credits単価は測定時の凍結条件であり、実アカウントの残高差・現時点の単価・円貨支出とは混同しない。
