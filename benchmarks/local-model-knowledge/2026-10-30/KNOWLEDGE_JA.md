# 作業別の使い分けと、失敗から得た知識

この記録は、保存された成功・失敗から得た作業配分の候補です。試験用の固定検査がある作業の結果であり、本番のRouterへ自動反映したルールではありません。[全体結果](README_JA.md)、[処理型別の数値](PROCESSING_TYPE_RESULTS.csv)と一緒に読んでください。

## Gemmaを中心に使いやすい作業

**入力、使うルール、変更箇所、出力形式を明確にできる仕事**です。例えば、指定項目だけの抽出、決まった分類への振り分け、条件に従う集計、既知の場所だけを直す編集です。

最初の500件では、Rustの問い合わせ分類・承認状態の小関数・既知バグの限定修正が各10/10、PPTの書式統一が10/10でした。ただしOfficeは、Hostが決めた部品・設定をGemmaが返し、Hostがファイルへ反映して検査する方式です。自由にPowerPointやExcelを操作し、資料全体を納品できたという意味ではありません。

業務500件では48/50処理型が10/10でした。汎用500件でも495/500でした。この範囲では、わざわざ別モデルへ渡し直すよりGemmaを中心にする根拠があります。一方、後の境界条件500件では39/50処理型が10/10、文書・計画などの新500件では36/50処理型が10/10でした。新しい条件まで広げた際の失敗も残します。

## 他モデルを候補にする理由

| 作業 | 候補と実測 | 使う際の条件・反例 |
| --- | --- | --- |
| カテゴリ別集計 | gpt-oss medium：業務・汎用の共通4例で4/4、平均13.8秒。Gemmaも4/4、19.7秒 | 小標本。JSONの外側の形式に違反しやすいため、値だけを見て採用しない |
| 区間の統合 | gpt-oss medium：同4/4、16.4秒。Gemma4/4、59.6秒 | 境界、重なり、空区間の仕様を固定する。日時全般に強いという結論には広げない |
| SQLで最新行を選択 | gpt-oss medium：同4/4、17.3秒。Gemma4/4、81.0秒 | 同時刻の優先順位、対象集合を指定する。任意DBの変更能力は未測定 |
| 項目抽出・規則表引き・ID正規化 | Qwen14：各4/4、平均7.8／2.9／5.8秒。Gemma各4/4、17.1／15.6／22.4秒 | 単純な入力と短い規則へ限定。境界条件100件では31/100で、複合処理の代替にはしない |
| 条項抽出・共通データ作成 | Qwen3.5 thinking：業務・汎用の各共通4例で各4/4 | 別のRust課題では思考込み32768 tokensの上限到達がある。小さいモデルでもVRAMや時間に余裕があるとは限らない |
| 引用部分の除去 | Devstral：追補でGemmaが誤った4例を4/4補完 | 以前の別の引用課題では失敗もある。契約が同じ処理へ限定して追加検証する |
| 三者照合 | 旧業務・汎用共通例でDevstral4/4、Gemma1/4 | 対象IDの範囲が曖昧だった。新しいorders_only明示課題ではGemma10/10。Devstralへの恒久割当ての根拠にはしない |

この表の速度差は、同じ小標本におけるAPI時間です。モデル切替を含みません。業務500件でのcold load観測はモデルにより約6〜21秒だったため、数秒の処理を毎回別モデルへ移すと、切替の待ち時間が利益を打ち消す可能性があります。同種の仕事をまとめる運用は検討できますが、その効果は未測定です。

## 失敗の読み方

### 上限で止まったもの

初期の失敗課題を使った後続検証では、Gemmaは思考ありの30件で27/30、残る3件が出力上限でした。上限・contextを見直した難しい12件では12/12になりました。同じ失敗課題の部分集合を使う検証なので、新しい課題数には加算せず、初期500件の結果も置き換えません。

この結果は「旧上限でのFAILだけでは能力不足を判断できない」という知識です。上限を増やせば何でも解ける、という結果ではありません。後の固定設定でもQwen3.5には上限到達が残りました。出力上限には思考tokensも含みます。

### 形式が違ったもの

gpt-ossは、値が正しくても外側の`result`がないなどの理由でFAILになりました。業務共通100件の形式違反22件中18件、汎用の24件中17件、境界条件の27件中18件では、外側の箱がない一方で値自体は一致していました。後から箱を補ってPASSへ変えてはいません。

Gemmaも、外側の形式を守っていても、内側の箱・型・配列順で失敗します。境界条件500件では、並び順だけの違いが14件、必要な内側の箱の省略が2件、二重JSON化・型違いが1件ありました。「JSONとして読めた」と「契約に合っている」は別です。

### 内容・コードを誤ったもの

境界条件500件では、Rustのコンパイル3件、コードテスト10件が失敗しました。金額の固定小数表現・i64境界を扱う処理はGemma2/10で、他4モデルも共通例では各0/2でした。難しい境界計算を別モデルへ渡すだけでは解決しません。

文書・計画などの追補500件では、計算の符号、最長一致、Base64などの内容・ルール誤りが15件ありました。他モデルが補えたのは10/15。残る5件は、台帳取消の2例、最長一致の1例、Base64の2例でした。明示されたLCSの同点規則3失敗も、補完できたのは1件です。

### 指示・採点が十分に明確でなかったもの

旧三者照合では、注文ID以外の請求IDも出すかが曖昧でした。新しい試験で対象をorders_onlyに限定するとGemma10/10でした。別の課題なので、文言修正だけの因果効果は分離していません。

境界条件の参照先探索では、回答先は10/10正しかった一方、証拠IDの違いで8件FAILでした。そのうち7件は、開始点のrequest.idを含める条件が十分に明示されていませんでした。残り1件には中間IDの省略がありました。

追補48失敗のうち25件にも、成功・拒否ラベル、無効入力の扱い、証拠IDなどの契約の曖昧さがあります。他モデルがそのうち20件で元の期待値に一致しても、それをすべて「推論が優れている証拠」とは扱いません。元FAILを保全し、指示を改善するための知識にします。

## Localへ渡す依頼に含めるもの

| 項目 | 明記する内容 |
| --- | --- |
| 作業 | 何を計算・抽出・変更するか。一度の依頼では責務を限定する |
| 入力と対象範囲 | 対象月、採用ID、除外条件、参照元、変更してよい場所 |
| 業務ルール | キャンセル、負数、丸め、閾値、同点、重複をどう扱うか |
| 出力 | 外側・内側のJSON構造、型、配列順、nullと項目なしの区別、証拠IDの範囲 |
| 検査 | 通常値だけでなく、0・空・境界・無効入力をどう確認するか |
| 不明点 | 決められない業務条件は人間へ確認する。AIが都合よく決めない |

Hostによる形式・範囲・コードの検査は有効ですが、仕事内容全体の正しさを保証しません。独立したAIの確認にも見落としがあります。この評価群では、試験側が検査を用意する費用、曖昧な依頼を明確にする費用、クラウドの計画・確認を含む総費用は測っていません。

目標は、Gemmaの利用率を増やすことではなく、**適した仕事を任せ、最終品質と全体費用を確認すること**です。この記録だけで自動fallbackや本番のモデル割当てを変更していません。
